## Read evidence labels literally

A synthetic fixture tests an implementation. A framework-component probe tests a component. A provider diagnostic tests a transport/configuration. A pilot tests a declared local slice. None becomes confirmatory evidence because its JSON schema passes or because it is tracked in Git.

Keep the original `data_kind`, protocol, configuration and source references with exported summaries. Preserve the distinction between scheduled, prepared, started, scorable, imported and completed. The active design's 322,164 opportunities are planned, including preparation failures.

Internal mock material from the discussion workflow is synthetic and ineligible for confirmatory analysis. Do not copy its numeric tables, confidence intervals, costs, preparation hours or simulated case explanations into public empirical claims. Later aggregate files require their own documented provenance; their status is not inferred from a filename.

## Before releasing execution evidence

Publish only material with a reviewed license/consent basis and complete task/configuration/evaluator provenance. Remove API keys, credentials, cookies, authorization headers, private account content and identifying browser artifacts. Preserve outcome/missingness denominators after redaction. Record which evidence could not be released and how a replicator can reconstruct an allowed fixture.

Raw screenshots, HARs, prompts, provider outputs and SQLite ledgers may contain sensitive content. Keep them in ignored, restricted storage. A file hash proves identity, not correctness, anonymization or permission to distribute.

For the ATA correction, use all 113 official cases and preserve 62 PASS / 51 FAIL. Historical 112-case summaries are not automatically valid after changing their denominator. Obtain and reconcile the actual case identities and executions before updating empirical conclusions.

## Citation and versioning

Cite [CITATION.cff](../CITATION.cff) and the exact commit used. A development package version is not evidence of a GitHub release. A persistent identifier will be added when an actual reviewed archival release exists; no placeholder DOI is supplied.
